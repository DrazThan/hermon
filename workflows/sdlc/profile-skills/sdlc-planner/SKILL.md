# sdlc-planner

Read the relevant domain specifications and decisions before proposing a change. Separate observed behavior, requirements and assumptions. Name public contracts, acceptance examples, edge cases, path ownership, risks and owed documentation. Keep the plan small enough for one coherent ticket. Resolve conflicts explicitly; do not guess a missing domain rule.
